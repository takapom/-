# 実行中ミッション変更とリアルタイム性

## 結論

実行中のドローンに対して自然言語でミッション変更を与え、挙動を安全に変える研究は学術的に有用である。理由は、初期ミッション生成だけでは、物理環境で本当に重要な「状況変化」「人間からの介入」「制約の追加」「失敗からの回復」を扱えないからである。

ただし、ここでいうリアルタイム性は、LLM が機体姿勢をミリ秒単位で制御することではない。研究として扱うべきリアルタイム性は、飛行中に入った自然言語変更要求を、現在状態・安全制約・残タスクと照合し、実行継続、再計画、保留、拒否、停止、着陸のいずれかへ一定時間内に振り分ける能力である。

## 学術的な意味

初期動作だけを自然言語で生成する場合、研究課題は「自然言語からミッションを作れるか」に寄る。この場合、生成、検証、実行の一回限りのパイプラインになりやすい。

実行中ミッション変更を含めると、研究課題は次のように上位化する。

> 自然言語で与えられる非同期な目的変更を、現在の飛行状態と安全制約に基づいて、どのように安全なオンライン再計画へ変換できるか。

この問いには、次の学術的価値がある。

- Human-UAV Interaction: 人間が飛行中のロボットへ自然に介入する設計を扱える
- Online Planning: 事前計画ではなく、状態変化を受けた再計画を扱える
- Runtime Assurance: 実行前検証だけでなく、実行中の安全保証を扱える
- Statefulness: 前回の指示、現在の位置、残タスク、失敗履歴を踏まえた言語理解を評価できる
- Mixed-Initiative Control: 人間、LLM、検証器、フライトコントローラの権限分担を研究できる

## 行う意味

実世界のUAV運用では、出発前に完全なミッションを決めても、飛行中に条件が変わる。

例:

- 進入禁止領域が途中で追加される
- 風、GPS品質、バッテリー、通信状態により安全余裕が変わる
- 人間が「やはり高度を下げて」「そこには入らないで」「今の地点をもう一度確認して」と指示する
- 観測対象が移動する
- 前方の障害や安全リスクにより、当初計画を続けるべきでない

このような状況では、初期ミッション生成だけでは不十分である。研究としては、自然言語インターフェースの価値が「プログラミング不要で最初の計画を作る」だけでなく、「運用中の人間判断を安全に反映する」点に広がる。

## 何がよくなるのか

リアルタイム性を入れると、次の価値を評価できる。

| 価値 | 内容 | 評価例 |
| --- | --- | --- |
| 適応性 | 飛行中の目的変更に対応できる | 変更要求の反映成功率 |
| 安全性 | 危険な変更を実行前に止められる | 拒否すべき変更の拒否率、制約違反数 |
| 継続性 | 全ミッションを中断せず安全に再計画できる | 再計画後のタスク完了率、停止回数 |
| 状態保持 | 現在位置・残タスク・前回失敗を踏まえられる | State Loss 率 |
| 人間介入性 | 操縦やコードなしに意図変更できる | 介入から反映までの時間、確認質問数 |
| 説明可能性 | なぜ変更を受けた/拒否したか説明できる | 拒否理由・修正理由の妥当性 |

## 解ける研究問い

リアルタイム性を入れるなら、研究問いは次のように拡張する。

RQ5: 飛行中の自然言語ミッション変更に対して、現在状態を考慮するハーネスは、状態を考慮しないハーネスよりも安全制約違反と不適切な変更受理を減らせるか。

RQ6: ミッション変更要求を、即時適用、次ウェイポイント後に適用、保留、拒否、緊急停止に分類するポリシーは、タスク成功率と安全性のトレードオフをどう変えるか。

RQ7: LLM の推論遅延や出力分散がある中で、どの時間制約までなら自然言語ベースのオンライン再計画が実用的に機能するか。

RQ8: 実行中の変更要求に対して、Mission IR の差分パッチ方式は、ミッション全体を再生成する方式よりも安全で安定するか。

## リアルタイム性のレベル分け

リアルタイム性を一つの言葉で扱うと危険である。少なくとも3層に分ける。

| レベル | 時間スケール | 担当 | 本研究での扱い |
| --- | --- | --- | --- |
| Control Real-Time | 10-100 ms | Pixhawk / ArduPilot | LLMを入れない。研究対象外 |
| Runtime Safety | 100 ms-1 s | Runtime Monitor / フェイルセーフ | 決定的ロジックで扱う |
| Mission Replanning | 1-10 s | AI Harness / LLM / Validator / SITL-lite | 研究対象 |

本研究のリアルタイム性は、主に Mission Replanning と Runtime Safety の接続に置く。つまり、LLM が遅くても、機体は安全にホールド、減速、ロイター、着陸できる構造にする。

## 実装として可能か

可能である。ただし、実装可能性は「飛行中にLLMが直接操縦する」ではなく、「飛行中に上位目標やウェイポイント、速度・高度上限、ジオフェンス、モード遷移を更新する」と定義する必要がある。

ArduPilot / MAVLink では、Guided mode や Offboard control interface を通じて、外部コンピュータから目標位置、速度、高度、方位、モード変更などを送れる。したがって、Raspberry Pi のような companion computer が、MAVLink 経由で実行中ミッションへ介入する構成は現実的である。

ただし制約もある。

- vehicle type によって使える MAVLink メッセージとパラメータ組み合わせが違う
- Guided mode でも、頻繁な更新に向くコマンドと向かないコマンドがある
- 位置・速度・姿勢のどのレベルまで外部から与えるかで危険度が変わる
- 通信遅延、LLM遅延、SITL検証時間により、即時反応には向かない
- 飛行中の緊急対応はLLMではなく、決定的フェイルセーフに委ねるべきである

## 推奨する実装境界

実行中変更は、Mission IR の差分パッチとして扱う。

```yaml
mission_patch:
  target_mission_id: mission_023
  apply_policy: next_safe_boundary
  changes:
    altitude_max_m: 1.5
    speed_max_mps: 0.6
    no_fly_zones:
      add:
        - id: zone_new
          shape: polygon
          points_local_m:
            - [1.0, 2.0]
            - [2.5, 2.0]
            - [2.5, 3.5]
            - [1.0, 3.5]
  safety:
    fallback_if_rejected: hold
```

重要なのは、ミッション全体を毎回再生成しないことである。変更要求は、現在実行中の Mission IR に対する差分として扱い、Validator が差分後の全体ミッションを検査する。

## 変更要求の分類

飛行中の自然言語指示は、すべて同じ扱いにしない。

| 分類 | 例 | 処理 |
| --- | --- | --- |
| Parameter Update | 「高度を1.5m以下にして」 | 次の安全境界で反映 |
| Route Patch | 「この領域を避けて戻って」 | 再計画後、Validatorを通す |
| Observation Request | 「今の地点をもう一度見て」 | hover/loiterを挿入 |
| Emergency Command | 「止まって」「着陸して」 | LLMを介さず即時安全動作 |
| Ambiguous Update | 「もっと安全に飛んで」 | 確認質問または保守的変更 |
| Unsafe Update | 「もっと低く障害物を越えて」 | 拒否または代替提案 |

## 適用タイミング

飛行中変更は、即時反映すると危険な場合がある。適用タイミングを明示する。

| ポリシー | 内容 | 使う場面 |
| --- | --- | --- |
| immediate_safe | 安全動作として即時反映 | 停止、ホールド、着陸 |
| next_safe_boundary | 次のウェイポイント、hover、loiterで反映 | 高度・速度・経路変更 |
| after_validation | SITLまたは軽量検証後に反映 | ジオフェンス追加、経路再計画 |
| reject_and_hold | 拒否してホールド | 制約衝突、曖昧、危険 |
| human_confirm | 人間確認後に反映 | 意図が複数解釈できる場合 |

## アーキテクチャ拡張

既存のアーキテクチャに、次の3層を追加する。

```text
Telemetry Stream
  ↓
State Estimator / Mission State Store
  ↓
Online Change Request Handler
  ↓
Mission Patch Generator
  ↓
Patch Validator
  ↓
Apply Policy Selector
  ↓
Runtime Monitor / MAVLink Command Adapter
```

### State Estimator / Mission State Store

現在位置、速度、高度、モード、バッテリー、残ウェイポイント、現在の制約、前回失敗を保持する。

### Online Change Request Handler

飛行中の自然言語指示を受け、緊急命令、通常変更、曖昧変更、危険変更に分ける。

### Mission Patch Generator

Mission IR 全体ではなく、差分パッチを生成する。

### Patch Validator

差分適用後のミッションが安全制約を満たすか検査する。

### Apply Policy Selector

即時反映、次の安全境界で反映、保留、拒否、緊急動作を選ぶ。

## 評価指標

リアルタイム性を評価する場合、追加する指標は次の通り。

- command_to_decision_latency: 自然言語入力から受理/拒否/保留判断までの時間
- command_to_effect_latency: 入力から機体挙動に反映されるまでの時間
- unsafe_acceptance_rate: 危険変更を誤って受理した割合
- safe_rejection_rate: 安全な変更を誤って拒否した割合
- patch_validity_rate: 生成されたミッションパッチの妥当率
- state_consistency_rate: 現在状態を正しく参照できた割合
- interruption_cost: 変更により失われたタスク進捗や余分な移動距離
- recovery_success_rate: 変更後も安全にタスクを継続・終了できた割合
- fallback_activation_count: hold、loiter、land、RTL が発火した回数

## 研究上のリスク

リアルタイム性を入れると、研究が広がりすぎる危険がある。最初から完全な動的環境を扱うべきではない。

避けるべきこと:

- 障害物認識、SLAM、複雑な動的回避まで同時に扱う
- LLMに速度指令や姿勢指令を高頻度で出させる
- 実機で未検証のオンライン変更をいきなり試す
- 「リアルタイム」を定義せず、何となく即時応答を目指す

最初の研究スコープ:

- SITL中心
- 低速・低高度・短いミッション
- 変更要求は高度、速度、ウェイポイント、ジオフェンス、停止/着陸に限定
- 変更タイミングは `next_safe_boundary` を基本にする
- 緊急命令だけ `immediate_safe` にする

## 追加する仮説

H4: 実行中ミッション変更を Mission IR 差分パッチとして扱う方式は、ミッション全体を再生成する方式より、状態喪失、制約違反、過剰修復を減らす。

H5: 変更要求を即時適用せず、安全境界で適用するポリシーは、応答遅延を増やす一方で、安全制約違反と軌道不安定性を減らす。

H6: 緊急停止・着陸・ホールドを LLM 経由にせず決定的ランタイム監視へ委ねることで、LLM推論遅延があっても安全性を維持できる。

## 関連研究との差分

既存研究には、自然言語でロボットタスクを計画する研究、安全なLLMロボット計画、UAVのオンライン計画がある。これらに対して、本研究は次の位置に置く。

- 対象をUAVに絞り、実行中の自然言語ミッション変更を扱う
- LLMの計画能力そのものより、LLM出力を安全に実行へ接続するハーネスを扱う
- オンライン再計画を、Mission IR差分、Patch Validator、Apply Policyとして分解する
- 実機制御ではなく、SITL中心の評価と限定実機確認にする
